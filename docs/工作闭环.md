# 同一套求职工作流程

所有使用者共用相同入口、规则、状态结构与工具。个人信息的私有存储不构成另一套工作方式。实例根位置由配置决定，现有用户与新用户都读取 memory/CURRENT_STATE.md。

本页是开始、推进、收尾与验收规则的唯一维护来源，适用于每次 OfferLoop 工作，不依赖旧会话记忆或本机 skill。

## 开始时

运行 `python -X utf8 scripts/workspace.py refresh`，打开输出的当前工作页。它直接回答当前方向、简历版本、已记录投递和反馈、笔面缺口及下一步。方向和检索范围不一致、材料修改后未复审、已投但缺回执等问题直接显示。不能只凭上次生成的页面推断数据仍是最新。

按本轮问题选择现用材料和直接调用方；不把读取整个目录、历史和全部技能作为默认准备步骤。没有变化的事实不重复调查，只有影响当前判断的缺口才补查。

新实例由 setup.py 初始化。已有实例先把旧记忆的有效结论迁入 memory/workspace.json，再用 refresh --adopt 接管当前页。只执行一次迁移，之后不走专属旧流程。

## 推进时：唯一写入位置

| 信息 | 唯一维护来源 | 其他文件怎么用 |
| --- | --- | --- |
| 个人事实、偏好和限制 | profile/投递数据.json | 各模块读取，不复制一份人设 |
| 当前推荐、理由、暂缓项、下一动作、未决条件 | memory/workspace.json | CURRENT_STATE 自动呈现，不再在多份 README 重写 |
| 实际执行检索范围与策略 | 实例 config/（路径可配置） | 与方向说明核对；范围更新会触发未对齐提示 |
| 当前简历与项目正文 | 内容线中的现用文件 | 状态中只登记路径、用途、待审/可投和对应内容哈希 |
| 原 JD、筛选结果、投递/沟通事件、回执和下一行动 | 本地 SQLite 台账 | 当前页直接读取；飞书承接人使用的看板与跟进 |
| 原始作答、题源、缺口和复验 | 训练台账与笔面线现用材料 | 使用统一 interview_drill.py，位置可配置 |
| 通用方法与工具 | 项目根 docs/ 与 scripts/ | 个人目录不另维护覆盖规则 |
| 行业渠道、报告读法、景气/护城河判据、可复用行业认识 | docs/行业线/ | 所有用户共用；个人 profile 不保存研究方法全文 |
| 投递平台适配、字段映射、空配置示例 | scripts/config/ | 实例仅填写个人范围和策略，通用能力不另复制 |

个人已确认偏好与当前推荐分开；尚在研究的方向不能作为已确认事实。PDF/DOCX 只有核对来源版本后才能标可投。文件修改时间不能证明审阅状态。真实业务时间可记在事件里，文档不按天建版本。

公司原始资料不复制进求职材料，个人数据不提交公共仓库。

## 收尾时

先更新受影响的事实源，再更新工作状态，最后刷新当前页。没有变化的栏目不必重复写。

`python -X utf8 scripts/workspace.py close --json -` 接收 `{"source":"本轮明确陈述或核实依据","updates":{...}}`。updates 只允许 direction、materials、next_actions、open_questions、retained_constraints、cloud，提供的栏目整体替换；读旧值后只改实际变化，保留尚未解决的事项。

direction 包含 status、primary、parallel、deferred、reason、scope_hash、profile_hash。核对方向与实际检索配置一致后，传 align_scope=true，同步绑定当前个人档案与检索范围的版本；只更新说明不能伪造用户确认。范围不一致时说明实际覆盖缺口，先保留提示再解决。

materials 每项包含 path、label、purpose、status、reviewed_sha256、note。未审核用待审阅，已确认的可投版本须有内容哈希和确认依据；修改后自动显示待复审。SHA-256 仅绑定版本，不能证明事实正确。项目说明可登记“在用，待补证”，不必全当简历审批。

onboard、assistant、pipeline 和 interview_drill 的正常 CLI 写入后刷新当前页。手工改文件的会话也必须收尾。刷新失败明确提示“业务已写入、视图未更新”，先刷新，不重复业务操作。

飞书不是另一份手工维护的总账。已有连接时按原同步流程预览、授权同步并读回；本地入口标明云端是否核过，不因本地更新就声称云端已同步。初始化、建档和收尾均不触发联系招聘方或投递。

## 新材料如何处理

先问它下次具体用于什么。当前决定进状态，简历和口述改现用正文，通用判据改 docs/ 方法，岗位或训练事件写台账。单次搜索摘录、比较稿和转换件在完成提炼与校验后清理，不创建日期报告、历史文件夹或第二份状态。仍承担恢复、防重、待复验的材料保留其实际用途。

四条线是职责，不要求四个一级文件夹。行业与投递的方法直接从 docs/ 进入；其个人判断在 memory、执行配置在 workspace/config、业务记录在运行台账。内容线和笔面线因为有直接打开的简历、项目卡、题源及作答而保留实际目录。旧实例剩余的一次性材料逐项核实后清理，不能把整个目录搬进 docs/，也不以改名隐藏积压。

同一问题有两份不同结论时，先显示冲突及依据，解决后更新唯一来源。不得通过增加第三份“最新说明”掩盖冲突。

替换或迁移必须一起处理新位置、旧文件、README、配置、脚本及实际调用该文件的技能或调度。先确认有效内容与未完事项已承接，再按授权清理具体旧文件；不能只改目录说明，也不能将积压整包移入隐藏目录或历史目录。删除前核对绝对路径、范围和链接类型，排除凭据、运行锁、未决写入、防重记录及 Git 元数据；裸仓库也要识别，不能只排除名为 `.git` 的文件夹。不能证明可删的对象保留具体原因和待核事项。

## 验收时

| 层次 | 必须有的依据 | 不能混称的状态 |
| --- | --- | --- |
| 本地完成 | 唯一事实源已更新；旧文件已按结论处理；现用入口和引用可用；当前页与台账一致 | 仅创建新文件、仅移动位置或仅修改说明，不等于治理完成 |
| 验证通过 | 文档改动检查内容与链接；影响路径、初始化或工具的改动执行相关检查或既有测试；保留失败和未知 | 未运行不写已通过，离线测试不等于真实招聘或业务成功 |
| 远端同步 | 在已有授权范围内发布后，核对 Git 远端提交或云端读回结果 | 本地修改、commit、发出请求不等于远端已更新；不需同步时明确不涉及 |

只执行与改动相关的必要检查，已通过且没有新变化不重复扩大测试。最终回复按实际结果说明改了什么、如何验证及尚未完成的事项；不要为证明收尾再生成清理日志、逐日总结或新检查点。阻塞只写回现有状态中下一次确实需要的部分，未知写入先回查，不能盲目重放。
