```powershell
node scripts/browser_pw.js --url <当前完整URL> fill-plan <私有计划JSON>
```

## 接口检索与投递清单｜2026-10-30核实

目标：在不碰浏览器的情况下，用接口（网页搜索 + web_fetch）跑通「检索 → 抓原 JD → 筛选 → 逐岗 ready 投递清单」，投递动作按“人点最后一下”交付。已实测能力地图：

| 渠道 | web_fetch 结果 | 结论 |
|---|---|---|
| 牛客 nowcoder.com | ✅ 返回完整 JD 正文 | 服务端渲染（SSR），社招/校招/实习详情页都可读，是当前唯一稳定的接口 JD 源 |
| BOSS m.zhipin.com | ❌ 跳转安全验证页 | 反爬，接口读不到正文 |
| 示例企业官网 careers 站点 | ⚠️ 仅标题＋loading 壳 | SPA，正文由 JS 渲染 |
| 滴滴 talent.didiglobal.com | ⚠️ 仅标题 | SPA |
| 阿里云 careers.aliyun.com | ⚠️ 仅标题 | SPA |
| 智联 zhaopin.com | ⚠️ 历史已知受阻 | SPA／反爬 |
| TCL zhaopin.tcl.com Ajax | ❌ unsupported content type | 接口不可用 |

流程（Agent 执行，脚本只做确定性部分）：

1. `pipeline.py plan` 取当前单元的检索词，或直接用 `web_search` 按“行业×城市×岗位词”检索。
2. `web_fetch` 抓候选原 JD 详情页；优先牛客（SSR），官网/BOSS/智联抓不到全文就标“需浏览器或人工”，不伪造。
3. 按 `AI时代公司与岗位过滤器.md` v4 逐岗筛选：校招/实习、硕士+年限硬门槛、城市不符→exclude；缺口→clarify；通过→shortlist。
4. `assistant.py import` 沿原 URL 入库（含 `research_scope` 映射与 `known_hard_mismatch`）。
5. 通过者 `pipeline.py prepare` 登记逐岗简历，`pipeline.py track` 登记投递入口、打招呼话术与下一行动。
6. `python -X utf8 scripts/ready_list.py` 生成 `投递线/投递清单.md`：每岗含投递入口、逐岗简历（哈希）、硬条件、打招呼/准备卡、下一行动。
   - `--scope shortlist` 只看初筛候选；`--scope all` 看全部；`--output` 指定输出。
7. 投递提交走[浏览器 CDP 执行通道](#浏览器-cdp-投递执行通道2026-10-30)：宿主机启动 Chrome → `browser_cdp.js` 驱动。投递后 `pipeline.py record` 登记真实回执与简历哈希，提交未知先对账不重投。

诚实边界：牛客主要承载校招/实习，社招 Agent 岗位样本少；社招主渠道（BOSS/智联/官网）无公开投递 API 且 SPA/反爬，接口既读不到全文、也投不了。投递动作本身走下方 CDP 浏览器通道。

## 浏览器 CDP 投递执行通道｜2026-10-30

目标：让 AI（DSH 优先，Codex 亦可）通过 CDP 驱动浏览器完成真实投递，人不下场。实测约束：BOSS/智联无公开投递 API；DSH 沙箱无法启动 Chromium（Chrome 启动即 exit 21、profile 未建、crashpad OpenProcess 被拒）；DSH 实现内无 playwright/puppeteer。所以浏览器必须在沙箱外的宿主机启动，DSH/Codex 只做 CDP 驱动。

架构：宿主机常驻一个带 `--remote-debugging-port=9222` 的 Chrome（专用 profile，登录态持久）→ `browser_cdp.js`（Node 22 内置 WebSocket）连 127.0.0.1:9222 驱动。DSH/Codex 都只是调用 `node .../browser_cdp.js`，不绑定某个 harness。

执行：

1. 宿主机运行 `scripts/browser_launch.cmd`，首次在弹出窗口登录一次 BOSS/智联。
2. `node scripts/browser_cdp.js status` 确认浏览器与标签。
3. `node scripts/browser_cdp.js read <岗位URL>` 验证观察通道（此前各后端在此超时）。
4. `read` 通过后，按真实页面 DOM 增量实现 `apply`（导航→打招呼→投递逐岗简历→回执核验），再接入 `pipeline.py record` 登记。

当前状态（2026-10-30 已实测）：`status`/`read`/`buttons`/`click` 已在宿主机 Chrome 上验证通过——BOSS 已登录、正文可读、可枚举按钮、可点击；此前各后端「观察通道超时」在 raw CDP 下不存在。`apply`（打招呼→投递→回执）下一步按实际 DOM 增量开发。登录/验证码/新协议仍由本人处理；接受 offer、离职、迁居、薪酬底线由本人决定。

## 每次运行与停止原因

| action | 执行 |
|---|---|
| discover | start领取当前单元→真实检索→import→complete；零结果也保存查询与证据 |
| research | pipeline claim→核JD、企业与准入→assistant finish；仅正文完整、硬条件及C/J过滤合格才shortlist |

有可行动增量时继续下一单元。单元上限用于及时落盘，不能解释为每天只能工作15分钟。行业方向选择、降薪/驻场等用户取舍未确定时不越权代定。

### 平台资料维护的执行效率｜2026-10-24

普通资料更新沿以下流程执行，不重复探索已验证路径。此流程不启用投递、HR消息或新的平台授权。

**先执行浏览器异常检查**：新平台登录前，以及导航超时/频闪/旧页面不变后，按下节运行`browser_health.py`。已报告频闪时立即停止登录/填写，不能因读取旧DOM成功而继续；仅在恢复并核验后接续。

1. 本地先运行下述`profile.py prepare`，从个人信息台账、当前简历和结构化读回生成字段差异及分模块正文。未变化字段作为跳过候选，执行前仍以当前模块读回确认，历史快照不等于当前页面。脚本已实现内容提取、日期校验、文件哈希、差异和读回比较；文件排版转换与网站自动填表不在本脚本内。
